The 600Hz build: what's confirmed, what's corrected, what's unverified.

Superseded the earlier 360Hz/NVIDIA-Pulsar direction with this AMD-based 600Hz target. Everything build-specific below is checked against vendor/official sources where a claim was checkable; a few items are carried through as-given because I couldn't verify them independently — flagged as such rather than silently endorsed.

Still true, regardless of build

Valve's Counter-Strike 2 listing publishes one tier — Minimum — for Windows and SteamOS/Linux, and no latency spec at all. Everything past "does it launch" — including this whole document — is a separate exercise Valve doesn't publish an answer to.

The 600Hz build

Confirmed — AMD

CPU — Ryzen 7 9800X3D

Real, 8C/16T, current best-in-class for this workload. AES-NI and PCLMULQDQ called out together is more precise than my own earlier answer: GNS's AES-GCM-256 needs both — AES-NI for the encryption step, PCLMULQDQ for the GHASH authentication tag calculation inside GCM. Both are unconditional on this chip; nothing to enable.

Confirmed, one correction — AMD

GPU — ASUS Dual Radeon RX 9060 XT 8GB

Real card, confirmed against AMD's own product page — RDNA4, 2048 shader cores, 8GB GDDR6, $300-class. It's DisplayPort 2.1a, not 1.4 (doesn't change anything for this specific monitor's own DP1.4 input, but worth knowing if you ever pair a higher-bandwidth display). VCN 4.0 is very likely wrong — VCN versions have tracked architecture generations (RDNA2≈3.0, RDNA3≈4.0), so RDNA4 should be VCN 5.0. I don't have a source pinning the exact number down with certainty, so treat this as "probably 5.0" rather than confirmed.

Confirmed, plus a real gap in the doc — BenQ

Display — BenQ Zowie XL2586X+

Real, current, in stock at multiple retailers — 24.1", Fast TN, 1920×1080, 600Hz, DyAc 2. What the doc doesn't mention: BenQ's own product page states you need Windows 11, updated to the latest version, for 600Hz to work at all — worth confirming before assuming the OS side is a non-issue. Both DP1.4 and HDMI 2.1 are listed by BenQ as supporting 600Hz at this resolution, so — unlike a 1440p target — bandwidth isn't the open question here; the OS requirement is.

Correction

RAM — G.Skill Flare X5 32GB DDR5-6000 CL36

The frequency is still right — DDR5-6000 is what holds AM5's Infinity Fabric at a 1:1 ratio with the memory clock, and that benefit doesn't depend on CAS latency. But CL36 is a real, measurable step down in timing tightness from the CL30 we established earlier in this build process as the actual sweet spot at this speed. Same frequency benefit, worse absolute latency. Not a functional problem, just not the tightest kit at 6000 — a CL30 kit at the same speed would be strictly better with no downside.

Confirmed

Motherboard + NIC — ASRock B650M Pro RS (mATX) (non-E) / Realtek RTL8125BG

The non-E reasoning is sound — this build isn't using PCIe 5.0 bandwidth for anything. The RTL8125BG's 32 MSI-X vectors checks out against a real driver capability dump from actual hardware, and quad-core RSS is confirmed via Realtek's own product listings. Both numbers in the doc are accurate — this directly informs the RSS script below, since 4 hardware queues is the real ceiling, not an arbitrary choice.

AMD Radeon Software (Adrenalin)

  • Above 4G Decoding + Re-Size BAR — real technology, correctly described (full VRAM addressing instead of small windowed chunks). The specific "real improvement to 1% lows in CS2" claim isn't independently sourced here — plausible, not confirmed.
  • Radeon Boost: Disabled — correctly described. It drops render resolution during fast mouse movement, which is exactly wrong for a game where flicks are the moment you need clarity, not less of it.
  • Radeon Anti-Lag 2: confirm it's actually on — right instinct. Supporting it isn't the same as it being enabled by default.

GameNetworkingSockets: why RSC/LSO don't touch this traffic

General mechanics, independent of which build.

RSC is TCP-only — confirmed via Microsoft's own driver docs. Zero interaction with GNS's UDP traffic regardless of NIC vendor. LSO is inert here for a cleaner reason: GNS fragments messages into MTU-sized pieces at the application layer before they reach the socket, straight from Valve's own repo — nothing oversized ever reaches the NIC for segmentation offload to act on.

Windows OS & NIC script

StepVerdict
Power plan, HAGS, overlay disablingStandard — uncontroversial
Set-NetAdapterRss -BaseProcessorNumber 2 -MaxProcessorNumber 8 -MaxProcessors 4Real params, documented conflict risk — see note
Interrupt Moderation → DisabledCorrect — right value this time, and the right DisplayName style for a Realtek driver (binary Enabled/Disabled, not Intel's graduated "Rate")
EEE / Green Ethernet / Idle Power Saving, each with -ErrorAction SilentlyContinueGood practice — correctly hedges against Realtek's inconsistent property naming across driver versions
Flow Control, LSO, RSC + netsh, PCIe ASPM via powercfgConsistent with what's already validated in this build's history
No -NoRestart on any Set- command, then a final Restart-NetAdapterInefficient, not wrong — see note
On the RSS command: Microsoft's own parameter reference notes MaxProcessorNumber and MaxProcessors are interdependent and "could cause conflicting settings" when both are set — which this script does. In this specific case they likely land on the same outcome (RSS populates only even-numbered logical processors on SMT systems per Windows' documented behavior, so 2→8 already resolves to four processors: 2, 4, 6, 8 — matching the RTL8125BG's real 4-queue ceiling either way), but "likely resolves the same" isn't "confirmed." Check Get-NetAdapterRss's IndirectionTable output after applying rather than assuming.
On restarts: without -NoRestart, each Set-NetAdapterAdvancedProperty call can cycle the adapter on its own — meaning this script may restart Ethernet five or six times before the explicit Restart-NetAdapter at the end even runs. Not broken, just needlessly disruptive. Adding -NoRestart to each `Set-` line and letting the final restart do the one real cycle is the cleaner version.

Power constraints (optional)

Correctly scoped by the doc itself as a thermals/noise exercise, not an fps one — CS2 doesn't stress a CPU's full power budget the way an all-core synthetic benchmark does, and the Curve Optimizer caution ("test, not trust blindly, validate with a stress test") is exactly right, chip-to-chip silicon variance is real.

One thing to double-check in your actual BIOS: the doc lists "PPT Limit (mW) to 88000." Consumer AMD BIOS UIs almost always present PPT in watts, not milliwatts — this reads like a units label error rather than a real mW field. Confirm what your specific BIOS screen actually shows before entering a number; if it's a watts field, the target value is 88, not 88000.

Router & ISP (Biznet + OpenWrt)

Bridge mode + PPPoE to eliminate double NAT is standard and correct. The CAKE parameters are consistent with well-established OpenWrt/SQM community guidance — overhead 44 is the commonly-cited PPPoE-over-Ethernet figure, mpu 84 matches standard minimum-frame guidance, and DSCP-marking outbound UDP for CAKE's diffserv prioritization (CS5 here) is a legitimate, real technique — not something I can verify the specific class-selector choice against a single canonical source, but the mechanism is sound. Measuring actual throughput before setting the 85–90% SQM ceiling, rather than trusting the plan's nominal number, is the right instinct — ISPs rarely deliver exactly what's advertised.

Bottom line

This build's CPU/GPU/RAM/monitor combination is genuinely ahead of what CS2 needs at 1080p Low — at these settings the game stays CPU-bound, so the GPU isn't the lever to chase further. The corrections above are all small: a units label, two parameters that might step on each other, a few redundant adapter restarts, a slightly loose RAM timing, one probably-wrong encoder version number. None of them are load-bearing errors — the overall direction of this build and script is sound, and notably better-targeted to its actual NIC (Realtek-appropriate property names, real hardware queue counts) than the more generic, Intel-flavored version worked through earlier in this document's history.
