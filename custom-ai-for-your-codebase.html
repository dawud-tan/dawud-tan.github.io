Build a Custom AI Assistant for Your Codebase

Start with an open-weight model and give it tools to search your repository, look up symbols, read files, and verify edits. Train a tiny model along the way to learn how language models work. Use the same repository tasks to find out whether running the finished assistant locally saves you money.

The slow path, with a checkpoint at every step

Pick one repository and record the commit you’ll use for exercises. The first three steps teach model fundamentals. The remaining five build the assistant you can use on that repository. Treat the time estimates as planning ranges. Move on when you can reproduce the checkpoint and explain the result with the tutorial closed.

1. Learn backpropagation in a few weeks

Build a scalar automatic differentiation engine in Python, then use it to train a small multilayer network. Work through micrograd and the first makemore lessons to connect the chain rule to a training loop and next-token prediction. Choose a smooth activation for a finite-difference check and include a test where one variable contributes to the loss along two paths.

Checkpoint. Train the network without a framework, reproduce the loss drop, and trace how gradients accumulate at a shared variable. Show that the gradients agree with your finite-difference check.

Karpathy’s Neural Networks: Zero to Hero · 3Blue1Brown on backpropagation

2. Build a tiny Transformer in one to two months

Implement a decoder-only GPT in PyTorch with causal self-attention, residual connections, normalization, and a feed-forward block. Build a byte-pair tokenizer alongside it and check that code with indentation and Unicode round-trips. For a roughly 10M-parameter exercise, try five layers, width 384, six heads, a vocabulary of 2,048, and tied input and output embeddings. Read the original Transformer paper after the exercise and compare its encoder–decoder architecture with your model.

Checkpoint. Your GPT trains and samples from a clean checkout. With dropout off, changing a future input token leaves the earlier logits unchanged. Explain each tensor dimension from the token batch to the logits.

Karpathy’s GPT and tokenizer lessons · Raschka’s Build a Large Language Model (From Scratch) · Attention Is All You Need

3. Train a tiny code model and inspect its limits

Train the same small model on code you’re allowed to use. A language slice of The Stack Smol is one option if you can meet its terms, including file-level license obligations. Hold out whole repositories where possible and remove duplicate files across splits. Save a checkpoint, continue training on a permitted snapshot of your own code, and compare both checkpoints on untouched files. Keep the code and answers for the later assistant evaluation out of adapter training.

Track training and validation loss. A falling training loss alongside a rising validation loss is evidence of overfitting. Compare autocomplete quality with answers to cross-file questions. A tiny model can learn formatting and common continuations while still missing how the project fits together. For scale, BigCode reports more than 3.5 trillion training tokens for StarCoder2-7B. The Chinchilla paper explains how model size and token count trade off under a compute budget.

Checkpoint. Show both loss curves and sample completions. Explain what the curves say about overfitting on your split, or what additional experiment would help distinguish it from undertraining.

4. Run pretrained weights locally

Load an instruction-tuned open-weight model in llama.cpp or Ollama. Qwen2.5-Coder-7B-Instruct and gpt-oss-20b are concrete starting points with different hardware requirements. Check the exact model’s license and runtime support. At four bits per weight, 8 billion parameters take about 4 GB of raw weight storage. Quantization metadata, higher-precision tensors, runtime buffers, and the key–value (KV) cache increase the memory you need. Longer prompts and concurrent requests can make the cache a substantial part of that budget.

Use dated coding benchmarks to shortlist other models, then compare them on your own tasks. Keep the model version, quantization, context limit, and sampling settings in your run log. Try short and repository-sized prompts at the same settings. Record peak memory, time to first token, and generation speed. The million-token comparison shows how the model’s architecture changes those costs.

Checkpoint. A local model answers a few coding questions with source excerpts you supply, within memory and latency limits you’re willing to use every day.

5. Run one small LoRA or QLoRA experiment

Train an adapter on a narrow behavior, such as responding in your team’s code-review format. Give the base model and the adapter the same held-out prompts and source excerpts, then score format compliance and correctness independently. Before you build retrieval, set aside 30 private repository questions with known evidence at the pinned commit. Use different questions for day-to-day tuning. Include a few unanswerable prompts in the broader evaluation to test when the assistant asks for evidence.

Checkpoint. Reload the adapter and reproduce the comparison. Explain which conventions it learned, where it regressed, and whether it earned a place in your harness.

6. Retrieve code by symbol, text, and dependency

Start with ripgrep for exact identifiers and paths. Use Tree-sitter to split Java, Kotlin, or Python files into classes or functions, storing the path, range, qualified name, and commit with each entry. Add SQLite FTS5 with BM25 for text search. Try embeddings and reranking only when measured failures justify them, such as a question phrased differently from the source.

Use a language server through the Language Server Protocol (LSP) for definitions and resolved references when the server and project support them. IDE rename can return an edit based on those same relationships. A Tree-sitter syntax tree gives you structure and candidates. Graphify (distributed as graphifyy) and Aider’s repo map show how a compact map can help prioritize files. Treat edges inferred from syntax as leads and verify them against source or compiler evidence.

Checkpoint. Compare against ripgrep on the 30 private, answerable questions. For a first target, find a required source range in the top five results on at least 24 of 30 questions. Record whether all required evidence was retrieved for multi-file questions, since finding one file can still leave the answer incomplete.

7. Write a read-only agent loop

Give the model a small tool list with operations such as list_dir, search, read_file with line ranges, and find_references. Validate the tool name and arguments in the harness, run the operation, return the result, and repeat until the model answers or hits a limit. Bound tool calls, wall time, and overall context. When a result is too long, return a bounded excerpt and its path and line range so the model can request the rest. Keep the original task and pinned commit in context.

Give tools access only to approved files inside the workspace, enforce file boundaries after resolving paths and symlinks, and treat repository content as data. Grammar-constrained JSON can help produce parseable calls. The harness still decides which calls are authorized. Keep a local trace of tool calls and paths and avoid collecting secrets in it.

Checkpoint. The assistant answers a multi-file question by finding a definition, tracing a caller, and citing source lines. The trace lets you replay its evidence. An unavailable file or exhausted budget produces a clear incomplete result.

8. Add a controlled edit-and-test loop

Start with one patch tool and named test commands. Run them in a disposable checkout inside a sandbox with no credentials or unnecessary network access. Limit writes to the checkout and cap test time and retries. Show the diff and test output for review before applying changes to the working branch.

Try a rename such as changing reserveSeat to holdSeat across 15 files. Ask the language server to resolve the symbol and propose a rename edit when available. Review that diff, then search the old name in configuration, reflective calls, templates, and generated sources. Verify the supported build targets and tests. A frontier model may do better at coordinating these checks. The language server, compiler, tests, and diff still supply the evidence that the edit is ready.

Checkpoint. In a known multi-file rename, the assistant updates the required callers, accounts for intentional old-name matches, and leaves unrelated symbols alone. The build and targeted tests pass, and you can explain the diff from the trace.

Rerun your private evaluation after each change to the model, prompt, or index. For answers, record correctness and whether the cited lines support the claim. For edits, record the diff review and test outcomes. When a task fails, check whether the right source reached the model. If it did and the model still struggled, try a stronger model through the same harness. You can rent GPUs for a larger open-weight model or use a hosted API where your repository’s data rules permit it.

What does a million-token context cost?

At one million tokens, full attention can use 131 GB just to store the context for one request. Linear attention and a selective state-space model (SSM) can carry the same input length in about 68 MB and 136 MB of recurrent state, respectively. The example models each have 16 GB of weights. Those weights are shared across requests, while each independent request needs its own context memory.

The estimates use three illustrative dense 8B models with 32 mixing layers, a single 1,000,000-token prompt, BF16 weights and KV cache, and FP32 recurrent state. The hardware is an NVIDIA H100 SXM with 80 GB of VRAM, 3.35 TB/s of memory bandwidth, and about 989 TFLOP/s of dense BF16 tensor compute. GB and MB are decimal.

How memory and work scale

Full attention stores a key and a value per historical position, per layer. With 32 query heads sharing 8 KV heads and 128 dimensions per head, the cache uses 1,000,000 tokens × 32 layers × 8 KV heads × 128 dimensions × 2 tensors × 2 bytes. Giving all 32 heads their own keys and values would raise the cache to 524 GB. Doubling the prompt length doubles the KV cache and decode work per token, and roughly quadruples the prefill attention work. FlashAttention tiles the exact calculation so the quadratic score matrix stays out of GPU memory.

Grouped-query attention · FlashAttention

Linear attention accumulates key–value associations in a shared state for each head. This example uses 32 heads with a 128 × 128 accumulator and a 128-element normalizer per head in each layer. The Mamba-2-style SSM keeps 128 state values for each of 8,192 internal channels per layer, plus a small BF16 convolution buffer. With those dimensions fixed, doubling the prompt roughly doubles prefill work and keeps state size and decode work per token steady.

What that means for latency

The dense projections and feed-forward layers add roughly 16 PFLOP per prompt and 16 GFLOP per generated token in each model. That brings a cold prefill to about 278 PFLOP for full attention and 16.1–16.2 PFLOP for either recurrent model. Chunking the prompt can bound temporary activation memory while carrying the cache or recurrent state across chunks.

  • Full attention on four H100s. Evenly sharded weights and cache take about 37 GB per GPU before temporary buffers. At 30–50% of aggregate peak compute, prefill takes an estimated 2.3–3.9 minutes. Decode streams about 147 GB of weights and cache across the GPUs per step. At 50–75% of aggregate memory bandwidth, that is about 15–22 ms per token before communication and other overhead.
  • Linear attention or an SSM on one H100. At the same compute utilization, prefill takes an estimated 33–55 seconds. The 16 GB of weights dominate decode traffic for one request, giving about 6–10 ms per token under the same bandwidth assumption, before other overhead.

These are analytical estimates. Peak VRAM and latency depend on the runtime, prefill chunk size, and GPU communication.

Why precise recall still matters for code

Full attention lets the current query score each earlier position individually, even when a detail only becomes relevant much later. In linear attention, similar keys can interfere as their values accumulate. A selective SSM learns what to keep or decay, so a rare identifier or exact quotation can fade as more tokens arrive. Larger recurrent states can improve recall. Across architectures, retrieval quality depends on training, context length, and the task.

For a repository assistant, test whether the model can find exact paths, definitions, and all relevant call sites at the prompt length you plan to use. The symbol and text search in step 6 can bring those source lines into the prompt when the model needs them.

When does a local assistant save money?

Frontier-model training puts the project in perspective. Cottier and colleagues estimated about US$40 million in amortized hardware and energy for the final training run of OpenAI’s original GPT‑4, released in 2023. In January 2025, Anthropic’s Dario Amodei said Claude 3.5 Sonnet cost several tens of millions of US dollars to train. These are historical figures with different accounting methods. Full development can also include staff, experiments, post-training, and evaluation. Your assistant’s budget starts from pretrained weights and pays for using them on real tasks.

Cottier et al. on frontier training costs · Amodei’s statement on Claude 3.5 Sonnet

Run the same workload and apply the same acceptance rubric to both setups. Include hardware depreciation or GPU rental, electricity, indexing, and maintenance for local inference. Include input and output tokens, cache or tool charges where applicable, and retries for hosted inference. Count human review time on both sides if it differs. Compare latency and acceptance rate alongside cost.

Cost per accepted task = total cost of all attempts ÷ number of accepted tasks. For example, if 100 tasks cost $12 locally and 60 pass, that’s $0.20 each. If the same tasks cost $15 with a hosted API and 90 pass, that’s about $0.17 each. These are illustrative figures. Use your own measured workload to decide whether to run locally, use an API, or route some tasks to each.

Frequently asked questions

Do I need to train an AI model from scratch for my codebase?

Start with pretrained open weights for a practical assistant. Connect the model to repository search and file-reading tools so it can use current code. Train a tiny model from scratch if you want to learn how language modeling works.

Should I use retrieval or fine-tuning?

Use retrieval for facts that change, such as where a function is defined or which modules call it. Use fine-tuning to teach recurring behaviors, such as a review format. Test each with held-out tasks.

Will running the assistant locally save money?

It depends on hardware, workload, and how many answers or edits you accept. Compare local and hosted costs on the same tasks, including failed attempts, maintenance, and review time where relevant. Divide each total by its accepted task count.

Can a small model rename a method across 15 files?

It can coordinate the task when the language server can resolve the symbol and the harness can verify the resulting patch. Check for references in configuration and reflective calls, then run the build and tests and review the diff.

How much memory does a 4-bit model need?

Eight billion parameters at four bits each take about 4 GB for the raw weights. Leave more room for quantization metadata, tensors kept at higher precision, runtime buffers, and context memory such as a key–value cache or recurrent state. Measure peak memory with the context length and concurrency you plan to use.
