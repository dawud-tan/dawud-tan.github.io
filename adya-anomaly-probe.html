Adya's isolation anomalies, tried against a live cinema booking app

A jshell script that tries to provoke every anomaly in Atul Adya's taxonomy through the public booking API of www.tiketbioskop.xyz:8443, and reports that none of them happens. This page is the manual: what each anomaly is, what it would look like at a cinema, why this app cannot produce it, and how to run the script yourself.

The script: adya-anomaly-probe.jsh (plain Java run by jshell, JDK 17 or newer). The fast path, once you have an empty showing and a signed-in cookie (steps below):

curl -fO https://dawud-tan.github.io/adya-anomaly-probe.jsh && chmod +x adya-anomaly-probe.jsh
export ADYA_SHOWING='https://www.tiketbioskop.xyz:8443/halls/<hall-id>/showings/<showing-id>'
read -rs ADYA_COOKIE && export ADYA_COOKIE        # paste the Cookie header, press Enter
./adya-anomaly-probe.jsh

The short answer

The booking application never sets an isolation level, so every transaction runs at PostgreSQL's default, READ COMMITTED. That level alone rules out the first half of Adya's list: dirty writes (G0) and the three kinds of dirty read (G1a, G1b, G1c). It does not rule out the second half: lost updates (G-cursor), read skew (G-single), write skew (G2-item) and phantoms (G2). Those four are closed by the design, at each place where a booking depends on them:

  • an EXCLUDE constraint that makes a second live claim on a seat impossible to write;
  • three row locks: FOR UPDATE on the showing, FOR SHARE on the seats being booked, and FOR UPDATE on the customer before counting their seats;
  • state changes written as a single conditional UPDATE … WHERE status = …, never as a read followed by a write;
  • the seat map read in one SQL statement.

Why "loosening the isolation level" cannot make them appear here. The app already runs at the loosest level PostgreSQL has: READ UNCOMMITTED is accepted but behaves as READ COMMITTED. So the tests in the repository make an anomaly happen by removing the design protection instead, such as the constraint or the lock. For G0 and the G1 family nothing can make them happen, because PostgreSQL has no setting that permits them.

Adya in five minutes

The ANSI SQL isolation levels are defined by three "phenomena": dirty read, non-repeatable read and phantom. These are worded in terms of locks, and they do not fit multiversion databases such as PostgreSQL. Atul Adya's 1999 MIT thesis, and the ICDE 2000 paper Generalized Isolation Level Definitions he wrote with Barbara Liskov and Patrick O'Neil, replaced them with conditions on the history of committed transactions. Any implementation can be checked against those conditions, whether it uses locking, MVCC or optimistic concurrency.

The history is drawn as a graph, the direct serialization graph. There is one node per committed transaction, and an edge from T1 to T2 whenever T2 depends on T1 in one of three ways:

  • ww write-dependency. T2 overwrote a version that T1 wrote.
  • wr read-dependency. T2 read a version that T1 wrote, or T1's write changed which rows T2's WHERE clause matched.
  • rw anti-dependency. T1 read a version and T2 then wrote the next one, or T2's write would have changed what T1's WHERE clause matched. T1 did not see T2, so T1 must come first.

A history is serializable when its graph has no cycle: there is some order in which each transaction saw only the ones before it. Each anomaly is a particular kind of cycle, or a read of data that should never have been seen.

PhenomenonAdya's condition on the committed historyFirst level that forbids it
G0 write cycleA cycle made only of ww edgesPL-1
G1a aborted readA committed transaction read a version written by one that abortedPL-2 (read committed)
G1b intermediate readA committed transaction read a version that its writer later overwrote itselfPL-2
G1c circular information flowA cycle made only of ww and wr edgesPL-2
G-cursor lost updateOn a single item, a cycle of one rw edge and ww edgesPL-CS (cursor stability)
G-single read skewA cycle with exactly one rw edgePL-2+ (and snapshot isolation)
G2-item write skewA cycle with one or more item rw edgesPL-2.99 (repeatable read)
G2 anti-dependency cycleA cycle with one or more rw edges, including ones from WHERE clauses (phantoms)PL-3 (serializable)

The difference between G-single and G2 is the number of anti-dependencies, and the two are easy to confuse. The textbook write skew (two on-call doctors who each see the other still on call and both go home) closes its cycle with two rw edges. That makes it G2, not G-single.

* A lost update at READ COMMITTED needs the read and the write in separate statements. A single UPDATE … WHERE that has to wait for a row lock re-evaluates its WHERE clause against the row that was just committed, so it cannot overwrite a change it did not see. That is the whole of the G-cursor defence below.

Why each one cannot happen here

These are the anomalies in the script's order, which is Adya's order: weakest level first. Seat labels are the ones the script picks on a fresh 40-seat hall.

G0 Write cycle (dirty write)

Definition
Two transactions each overwrite something the other wrote, so the final state mixes both. T1 writes x and T2 overwrites it, while T2 writes y and T1 overwrites that.
At the cinema
Two couples book the same pair at the same moment, one clicking left to right and the other right to left. Each goes home with one seat of the pair.
The probe
Four holds, A3+A4 and A4+A3 twice each, released at the same instant on four separate connections, three rounds. It checks that exactly one order has both seats, that the others have neither, and that the seat map shows each seat taken once.
Why not here
A claim on a seat is a write. PostgreSQL never lets two transactions hold uncommitted writes to the same row or the same pending constraint entry: the second one waits until the first commits or rolls back. That is how writes work at every level, not an isolation setting. On top of that, a hold is all-or-nothing. BookingService.holdInternal inserts seat by seat under a SAVEPOINT. On a 23P01 it rolls back to the savepoint, withdraws the seats it already inserted, marks the order failed, and commits that record, so no hold ever commits part of a pair. Every hold also opens with SELECT … FOR UPDATE on the showing row, so holds on one showing run one at a time.
Made to happen in
Nowhere. There is no PostgreSQL setting under which it can occur.

G1a Aborted read

Definition
A transaction reads a version written by a transaction that then aborts.
At the cinema
The seat map shows a seat claimed by a booking that never went through.
The probe
24 one-seat holds, on two lanes, on a seat the script already holds (A1). Each claim is written into the table, then rejected with 23P01 and undone by ROLLBACK TO SAVEPOINT, while three anonymous viewers read the seat map continuously. A read of a rolled-back claim would show A1 twice, because the seat map joins seats to their live claims. The probe checks that no read shows any seat twice.
Why not here
MVCC. A reader sees only versions whose transaction had committed when its statement began. A rolled-back version is invisible to everybody, forever. PostgreSQL has no dirty reads to switch on. The application adds its own version of the rule: seat-availability push notifications are sent only after a booking commits, so nobody is told about a change that could still roll back.
Made to happen in
Nowhere. PostgreSQL has no setting that permits it.

G1b Intermediate read

Definition
A transaction reads a version that its writer later overwrote before committing: a half-finished state.
At the cinema
During somebody's failed block booking, four seats flicker to "held" and back.
The probe
24 holds of A8+A9+A10+B1+A1. The first four are written as held. Then A1, already taken, fails, and the four are rewritten cancelled before the transaction commits. Three viewers poll meanwhile. The probe checks that no read ever shows those four as taken, and that they are free afterwards.
Why not here
The same MVCC rule. Each row is read as of the last commit before the statement began, never as a version its writer replaced before committing. The held versions existed only inside the doomed transaction.
Made to happen in
Nowhere.

G1c Circular information flow

Definition
A cycle of dependencies with no anti-dependency in it: each transaction read something the other wrote.
At the cinema
Two couples reach for one pair from opposite ends. Each sees the other's half-made booking, both are told the seats are gone, and the pair goes unsold.
The probe
A5+A6 and A6+A5 at the same instant, three rounds. Each hold writes its first seat and then goes for the seat the other wrote first. For both to be refused, each must have read the other's uncommitted claim, which is a wr edge each way. The probe checks that exactly one of the two gets the pair every time, and never neither.
Why not here
A hold only ever meets someone else's claim through the EXCLUDE check, and PostgreSQL's check never acts on an uncommitted claim. It waits for the claiming transaction to commit or roll back, then decides. So one of the two always finds either nothing or a finished booking, and gets the pair. READ COMMITTED, PostgreSQL's floor, forbids G1c by definition. On one showing the two holds also queue on the showing's row lock, so the second does not even start until the first has finished.
Made to happen in
Nowhere.

G-cursor Lost update (ANSI P4)

Definition
Two transactions read the same row, and both write it based on what they read. The first write is silently overwritten.
At the cinema
A customer cancels a seat while the order is being confirmed, and the cancellation is swallowed: the seat stays sold. At the door, the same shape would let one barcode admit two people.
The probe
Hold B4+B5. Then confirm the order and cancel B4 within a few milliseconds of each other, six rounds. A lost update needs the cancel to commit inside the confirm's read-then-write window, and that window's width is unknown from outside the server. So instead of one fixed timing, the rounds sweep an offset of up to 20 ms either way: together; each side 20 ms ahead; each side 5 ms ahead; the confirm 10 ms ahead. Released exactly together, one side tends to win every time. The probe checks that B4 always ends cancelled, and that the order ends in one of the two states a serial order produces:
• confirm, then cancel: order confirmed, B5 confirmed;
• cancel, then confirm: the confirm is refused because a seat is no longer held, so the order stays pending and B5 stays held.
Why not here
READ COMMITTED does allow lost updates when an application reads in one statement and writes in the next. This app never does that. Each change is one conditional UPDATE:
• confirm is … WHERE status = 'held';
• cancel is … WHERE status IN ('held','confirmed');
• the admission scanner is … AND admitted_at IS NULL.
When two collide, the second waits for the first's row lock and then re-evaluates its WHERE clause against the row that was just committed. It cannot overwrite a change it did not see.
Made to happen in
Any read-then-write split over two statements. AdmissionRescanConcurrencyTest races eight scans of one ticket and asserts exactly one admission. The tree has no weakened twin of it that shows the double admission.

G-single Single anti-dependency cycle (read skew)

Definition
A reader sees part of the database from before a commit and part from after it: a state that never existed. The cycle has exactly one anti-dependency: the reader read x before the writer changed it, and read y after.
At the cinema
The seat map shows one seat of a two-seat order as held and the other as free.
The probe
Three rounds of: hold B2+B3, then confirm the order, while three viewers poll. It checks that every read shows the two seats in the same state. The script also reports how many reads saw them free, held and confirmed, which shows that the reads really did span both commits.
Why not here
READ COMMITTED does permit read skew, but only across statements. The seat map is one SQL statement (every seat left-joined to its live claim), and each statement reads one snapshot, so a commit is seen whole or not at all. Where a hold decides from several reads, it locks what it read: the showing FOR UPDATE, the seats FOR SHARE, and the customer FOR UPDATE.
Made to happen in
Reading the two seats with two statements at READ COMMITTED. The tree has no test for it.

Where read skew is still possible, and harmless: an order's own page reads the order and then its seats in two statements. A reload that lands exactly between them during a confirmation can show "pending" above seats that are already confirmed. That render decides nothing, and the next one is right.

G2-item Item anti-dependency cycle (write skew): the double booking

Definition
Two transactions each read something the other is about to change, and both act on what they read. That makes two anti-dependencies, one each way.
At the cinema
Two customers turn up with tickets for F7.
The probe
Eight holds on A7 at the same instant, three rounds, alternating between two accounts if you give it two. It checks that exactly one wins each round, that every loser is refused "just taken", and that the seat map shows the seat taken once.
Why not here
A booking that asked "is F7 free?" and then inserted a claim would be classic write skew. Both see the seat free and both claim it, and READ COMMITTED and REPEATABLE READ both let that through. This app never asks. A hold just inserts its claim, and
reservation_no_overlap EXCLUDE USING gist (resource_unit_id WITH =, period WITH &&) WHERE (status IN ('held','confirmed'))
rejects a second live claim on the same seat for an overlapping time at write time, the way a unique index would. It works at any isolation level and surfaces as 23P01, which is never retried. "Just taken" is the message that 23P01 path produces and nothing else produces, so every loser in the probe was refused by the constraint itself.
Made to happen in
SeatBookingConcurrencyDifferentialTest builds the schema from the real migration with the constraint stripped out, runs the same eight-way race, and all eight succeed. Note that it removes the constraint rather than weakening isolation, because there is no weaker isolation to go to.

A precise footnote. A claim is a new row, found by a predicate (this seat, an overlapping time, a live status), not a new version of an existing row. So in the "ask, then insert" version the read is a predicate read, and its cycle strictly meets Adya's G2 condition. The project's design notes file it under G2-item because it concerns one known seat. Either way, the constraint closes it by turning the predicate conflict into a write conflict on an index entry.

G2 Anti-dependency cycle over a predicate (phantom)

Definition
Each transaction's COUNT or WHERE clause would have come out differently had it seen the other's insert, and both act on their count.
At the cinema
One person with two tabs gets past the 10-seats-a-day limit. That limit exists for exactly this person: a scalper.
The probe
One account already holds 2 anchor seats that day. It sends two holds of 5 seats, on two showings of the same day, at the same instant. One hold fits (2 + 5 = 7). Both do not (2 + 5 + 5 = 12). The probe checks that one succeeds and the other is refused by the daily cap, whose message counts the first one's seats: "You already have 7 seats for showings on …, and the limit is 10 a day."
Why not here
The rows that would breach the cap do not exist yet, so there is nothing to lock. READ COMMITTED, and REPEATABLE READ too, would let both holds count 2 and both insert. So the hold locks the customer's own row, with SELECT … FOR UPDATE in CustomerRepository.findByIdForUpdate, before counting. That serialises one customer's holds and nothing else. SERIALIZABLE would also catch it, at the price of 40001 retries on every hold, and the lock does it at READ COMMITTED. The first-booking rule ("the first booking on a showing must be for at least 2 seats") is also a count, and it is serialised by the showing's FOR UPDATE.
Made to happen in
DailyPurchaseCapConcurrencyDifferentialTest runs four holds on four showings of one day, so that their showing locks do not overlap, with the customer lock left out. All four pass the count, and the day ends at 12 seats against a cap of 10. Its twin with the lock, DailyPurchaseCapConcurrencyTest, lets exactly three through. Like the other differential tests, it removes the protection rather than weakening isolation.

The race that is not an Adya anomaly

A booking reads the showing as on sale. Staff cancel the showing. The booking commits afterwards anyway. That is a ticket for a showing that had already been cancelled, the last row of the table. It has one anti-dependency and no edge back, so it is not a cycle. "Book, then cancel" is a perfectly valid serial order, and no isolation level objects, not even SERIALIZABLE. What is wrong is that the booking's check went stale before it committed: the cancellation committed in between. The business rule is that nothing may be sold once a cancellation has taken effect. That is a rule about when things commit, and serializability of any flavour, strict or not, says nothing about it for two transactions that overlap in time.

The fix is SELECT … FOR UPDATE on the showing row as every hold's first statement. Whichever of the two reaches the row first, the other waits, then reads the current status. SessionCancellationRaceDifferentialTest reverts it to a plain SELECT and gets the orphaned hold. The script does not probe it because cancelling a showing needs a staff account, and because it is not on Adya's list. It belongs on this page anyway: knowing where the taxonomy stops is part of knowing it.

Step by step: running the script

  1. Check the tools. You need JDK 17 or newer (for jshell), bash, an env that understands -S (GNU coreutils 8.30+, or macOS/BSD), and outbound access to port 8443. 
    jshell --version        # jshell 17 or newer
env --version | head -1 # GNU coreutils 8.30 or newer (macOS: env -S is built in)
  2. Download the script, and read it. It is one file of plain Java. It sends only what a customer's browser sends, and it cancels everything it books. Reading it before giving it your session cookie is the right instinct. 
    curl -fO https://dawud-tan.github.io/adya-anomaly-probe.jsh
chmod +x adya-anomaly-probe.jsh
less adya-anomaly-probe.jsh
  3. Make two showings for it (staff). Signed in as staff, open /admin, pick a hall of about 30 seats or more, and use Create showing twice:
    • both on the same day, at least an hour from now, and not overlapping (for example 13:00–15:00 and 17:00–19:00);
    • with a label such as Adya probe 1, and no film. A film with an age rating makes every hold record an age attestation for your account, and the script refuses such a showing.
    A new showing is on sale immediately. Use fresh, empty ones: the script only ever touches free seats, but on an empty showing the final seat map shows at a glance that everything was given back.
  4. Copy the two seat-map addresses. Open the hall's public page, https://www.tiketbioskop.xyz:8443/halls/<hall-id>. The hall id is the one in the admin page's address. Press View seat map on each showing and copy the address bar. It looks like this: 
    https://www.tiketbioskop.xyz:8443/halls/<hall-id>/showings/<showing-id>
  5. Sign in as a customer. In a browser, open /login with an ordinary Google account. The platform-admin account cannot hold seats. Use one that has no other bookings on that day, because the daily cap counts them. The sign-in lasts about an hour, which is plenty; the run itself takes one or two minutes.
  6. Copy the session cookie. Open developer tools (F12), go to Network, and reload. Click the first request (the page itself), then Headers, then Request Headers, then Cookie. Copy the whole value. The important part is q_session=…. A large session is split into q_session_chunk_1, _2 and so on, and copying the whole header takes them all. The cookie is HttpOnly, so document.cookie in the console will not show it. The script drops booking_lang by itself, because it reads the refusal messages in English.
  7. Hand both to the script, keeping the cookie out of your shell history. 
    export ADYA_SHOWING='https://www.tiketbioskop.xyz:8443/halls/…/showings/…'
export ADYA_SHOWING_2='https://www.tiketbioskop.xyz:8443/halls/…/showings/…'
read -rs ADYA_COOKIE && export ADYA_COOKIE   # paste, then Enter; nothing is echoed
    Settings are environment variables because jshell passes no arguments to a script. A cookie on a command line would also be visible to every user of the machine through ps.
  8. Dry-run first. This reads the two seat maps and /orders, checks the rules and your session, prints the seat plan, and writes nothing: 
    ADYA_DRY_RUN=1 ./adya-anomaly-probe.jsh
  9. Run it. 
    ./adya-anomaly-probe.jsh; echo "exit status: $?"
    To make the races between two people, sign in with a second Google account in a private window, copy its cookie the same way, and export ADYA_COOKIE_2. To run a subset: ADYA_ONLY=G0,G2-item ./adya-anomaly-probe.jsh.
  10. Tidy up. The showing is empty again when the script ends; it prints the final seat map to prove it. Close or cancel the two probe showings in /admin so customers do not find them, and sign out. The cookie you copied stays a working credential until it expires, so treat the terminal it is in accordingly.

Reading the output

Each probe prints what it did, round by round; one line on what it would look like at the cinema; a why not here paragraph; and a verdict:

  • NOT OBSERVED: every attempt ended the way a serial order would have ended.
  • OBSERVED: the anomaly happened. The script then exits with status 1.
  • INCONCLUSIVE: an attempt was refused for a reason other than the one being probed, such as a cap you had already reached, so the attempt says nothing.
  • SKIPPED: the probe does not apply. For example, G2 is skipped if the deployment has no daily cap, or if the two showings fall on different days.

Exit status: 0 no anomaly observed, 1 an anomaly observed, 2 could not run or not clean. For G1a, G1b and G-single the script also reports how many seat-map reads were in flight alongside a write that could have leaked. That count uses client-side timing, so it is an upper bound on how hard the window was actually tried.

What a run leaves behind, and its load

  • Seats. Every hold the script makes, it cancels again. The final seat map is printed to prove it. If a run is interrupted, a hold expires by itself within 10 minutes. A confirmed seat (the G-single and G-cursor probes confirm some) does not expire, so cancel anything left over at /orders. The script prints each order's id as it goes.
  • History. Your account's order history keeps the probe's cancelled and failed orders, and the tenant's audit log keeps a row for every change. Both are append-only by design; the audit log is a hash chain, and it is meant to be impossible to tidy up. Run it on a demo tenant, not on a cinema's live catalogue.
  • Load. A default run sends about 150 writes and a few hundred reads over a minute or two; the script prints the exact counts at the end. Most reads go to the seat-map fragment, the endpoint every open seat-map tab already polls every three seconds. The three seat-map viewers pause 100 ms between reads, and only watch while a probe is writing. The office server shares its CPU with another production application, which is why the repository's load-test harness refuses to target it at all. This is a correctness probe, not a load test, so keep ADYA_ROUNDS modest.
  • Notifications. Every hold, confirmation and cancellation that succeeds sends a seat-availability push to anyone watching that showing's seat map with notifications allowed. A run makes dozens of them, and they are not throttled. Keep the probe showings' seat maps closed in any browser where you have allowed notifications. The script's own viewers are anonymous and subscribe to nothing.
  • Identification. Every request carries User-Agent: adya-anomaly-probe/1 (jshell; +https://dawud-tan.github.io/adya-anomaly-probe.html), so an operator reading the logs can see what it was.

What a live probe can and cannot show

A probe shows absence in the attempts it made. It does not prove impossibility. The windows it aims at are milliseconds wide, and the reads that happen to land in them are a sample. What makes each anomaly impossible is the mechanism named in its card. The script's job is to show that behaviour on the real server, over the real network, with the real configuration, which no unit test can do.

  • On one showing, holds queue on the showing's row lock. So the races on one showing (G0, G1c, G2-item) exercise that lock as much as the constraint. The losers are still refused by the constraint itself: "just taken" is only ever produced by the 23P01 path. The lock decides the order they arrive in, and the constraint decides who gets the seat. A race between two phones is a demonstration. The proof is the differential test.
  • G2 needs two showings to mean what it says. With only ADYA_SHOWING, both holds also queue on that showing's lock, and the per-customer lock is never the only thing between them.
  • One customer by default. Without ADYA_COOKIE_2, "two customers" are two connections of one account. The constraint does not care who asks. With a second account, the races are between two people.
  • Not covered: the counter channel, QRIS payments, the admission scanner and seat-map relayouts. Each needs staff credentials or money. They have their own tests in the repository (SeatRetirementRaceTest for relayouts, AdmissionRescanConcurrencyTest for the scanner).
